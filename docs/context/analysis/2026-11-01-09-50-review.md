# Repository hygiene, workflow hardening, and Rust test audit

**Objective:** assess the repository’s current hygiene, the quality of the Rust implementation, the real workflow in use, and the gap between local developer checks and GitHub-enforced checks.

**Scope:** Rust crates, repo automation, hooks, documentation context, and repository governance.

**Method:** repo structure audit, file inspection, code search, hook review, and policy comparison against GitHub Actions best practice.

**Outcome:** the repo is well structured and thoughtful, but it is not yet fully hardened at the repository-management level. The strongest gap is the absence of an external CI workflow.

## 2. Executive summary

The repository is, in a broad sense, disciplined and well designed.

Strong signals:

- `Cargo.toml` has explicit workspace-level lints and strict Clippy policy.
- The project uses `BTreeMap` and deterministic stream naming in `crates/pcfm-core/src/rng.rs`.
- The project documents invariants and design limits directly in the code, rather than leaving them implicit.
- Local developer hygiene is already present via `.githooks/pre-commit`.

Risk area:

- The repo lacks an external enforcement gate on GitHub. This means the same checks are not guaranteed for PRs and external contributors.

This is not a codebase-wide issue. It is a governance and automation gap.

## 3. Current workflow: what exists today

The current workflow is local, not remote.

Evidence:

- `.githooks/pre-commit` exists and runs:
  - `cargo fmt --all -- --check`
  - `cargo clippy --workspace -- -D warnings`
  - `cargo test --workspace`

File inspected: `.githooks/pre-commit:1-31`

This is a good local protection layer. However, it has three important limitations:

1. It is only active if the developer installs the hooks.
2. It is bypassable with `--no-verify` or by pushing directly without the hook.
3. It does not produce repository-visible enforcement for PRs.

In other words: it is good engineering hygiene, but not sufficient for a public project with PR-based review.

## 4. Why GitHub Actions is the right next step

### Advantages

- Remote enforcement on every push and pull request.
- Prevents “works on my machine” drift.
- Ensures that `fmt`, `clippy`, and tests are all enforced before merge.
- Produces logs and history for regressions.
- Makes repo policy visible and non-optional.

### Disadvantages

- Introduces a runtime cost and some maintenance overhead.
- Requires the workflow to be kept in sync with Rust versioning.
- A too-strict workflow early can block contributors if the project is still iterating rapidly.

### Best fit for this repo

For this repository, the positive outweighs the negatives. The project is already very strict about determinism and code hygiene; a CI workflow would add the missing non-optional enforcement layer without adding much complication.

## 5. Rust audit: what is strong

### 5.1 Deterministic architecture is coherent

`crates/pcfm-core/src/rng.rs` is the clearest example of a design centered on determinism.

What is good:

- named RNG streams are isolated
- stream derivation depends on a world seed + stream name
- empty names are rejected explicitly
- tests cover same-seed, different-seed, and name-isolation semantics

This is consistent with the project doctrine and with the requirement to prevent surprising RNG drift.

### 5.2 Event bus semantics are explicit

`crates/pcfm-core/src/event_bus.rs` defines a simple but coherent model:

- queue before dispatch
- insertion-order event processing
- registration-order per-kind handlers
- deterministic single-threaded dispatch semantics

This is exactly the sort of API that benefits from direct documentation and unit testing, and the code does that.

### 5.3 Lints are not accidental

`Cargo.toml` states workspace-level `unsafe_code = "deny"` and Clippy `correctness = "deny"`. This is a meaningful signal: the project is trying to keep the Rust surface auditable and resistant to misuse.

This is not just stylistic; it is governance by compiler.

## 6. Rust audit: what deserves attention

### 6.1 Panic propagation is a real design limitation

The key code-level finding is in `crates/pcfm-core/src/event_bus.rs`.

Commented behavior:

- the bus docs explicitly say a handler panic propagates
- queued events are lost during a panic path
- the limitation is acknowledged, not hidden

This is not “bad code,” but it is a meaningful risk. In a simulation engine, a panic in one event handler can disrupt the state evolution unexpectedly.

This should be treated as a backlog item, not as an emergency. But it is definitely worth tracking.

### 6.2 Unit tests exist, but deeper test layers are still missing

The repository already has unit tests in core modules, such as `rng.rs` and `event_bus.rs`, which is good. But for a project with determinism as a central doctrine, the test suite should expand beyond simple unit assertions.

What I would add:

- golden determinism tests for full-world state snapshots
- property-based invariants for stream behavior
- scenario smoke tests for CLI runners
- failure-path tests for panic boundaries and invalid state transitions

## 7. Recommended deeper tests

### T1 — Golden determinism tests

Goal: same seed + same scenario => same state hash.

Recommended checks:

- same seed, same world -> same match result
- different seed -> different result hash
- same state after round-trip serialisation

This is the most important test class for this project.

### T2 — Property-based RNG tests

Goal: verify broad invariants, not just a few examples.

Recommended checks:

- empty stream names always fail
- same world seed + same stream name => identical sequence
- different names produce non-identical sequences
- inserting a new stream does not shift existing outputs
- `next_unit` stays within `[0, 1)`

These are a perfect fit for `proptest`.

### T3 — Event-bus failure-mode tests

Goal: make the panic policy explicit and reproducible.

Recommended tests:

- handler panic does not silently pass unnoticed
- event dispatch order remains stable under normal conditions
- multiple subscribers for the same event keep registration order
- failure path has a deterministic test outcome

### T4 — CLI smoke tests

Goal: ensure user-facing tools remain stable.

Recommended checks:

- `cargo run --bin pcfm-demo` completes for a small known fixture
- test-runner list/check commands exit successfully
- JSON/text output stays stable enough to be compared against a baseline

### T5 — Registry/coverage tests

Goal: ensure each feature has at least one exercising scenario.

Recommended checks:

- each event kind has a scenario
- each stream contract is in use by a test
- impossible or invalid states are tested as negative cases

## 8. Recommendation for workflow implementation

A CI policy that matches the current local hook would be the right enforcement layer.

Proposed step set:

- checkout
- install Rust 1.85 toolchain
- `cargo fmt --all -- --check`
- `cargo clippy --workspace -- -D warnings`
- `cargo test --workspace`

Optional future hardening:

- `cargo deny check`
- `cargo audit`

This is the ideal compromise between strictness and practicality for this repo.

## 9. AI-readable interpretation of the report

This repository is not “dirty” in the usual sense. The code is explicit, the docs are strong, and the local enforcement is already more disciplined than average.

The real issue is not Rust quality. It is the lack of remote enforcement.

The AI should read this report as:

- codebase: structurally good
- workflow: only partially hardened
- test depth: adequate for a first prototype, but not yet mature for a doctrine-first deterministic engine
- most valuable next move: add GitHub Actions and deepen property/golden tests

## 10. Final verdict

The repository looks intentionally designed and disciplined. It has a solid code foundation and a clear local developer workflow. The main missing layer is repository-level enforcement via GitHub Actions, and the second most valuable improvement is broader deterministic test coverage.

This is a healthy project, not a chaotic one. It just needs the next layer of automation and a slightly deeper test ladder to become hardened rather than merely tidy.

**Status:** positive, but not yet “fully hardened.”
