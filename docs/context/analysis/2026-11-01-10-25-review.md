# Repository hygiene, workflow hardening, and Rust test audit

**Goal:** evaluate whether the project is clean, disciplined, and sufficiently hardened at the repository level, with a specific focus on Rust code quality, local automation, and GitHub enforcement.

**Scope reviewed:** `Cargo.toml`, `.githooks/`, `.github/`, `crates/pcfm-core/src/*`, `docs/context/analysis/*`.

## Summary

The repository is in a good state overall. The Rust code is intentional, structured, and mostly free from obvious anti-patterns. The project already has a solid local quality gate via `.githooks/pre-commit`, and the workspace lints are stricter than average.

The main gap is not Rust quality itself; it is repository governance. The repo currently lacks a GitHub Actions workflow, so the same checks are not enforced remotely for PRs and pushes. That makes the project easier to bypass and weaker as a public contribution pipeline.

## What is already good

### Local quality gate exists

The repo already has a pre-commit hook:

- `.githooks/pre-commit` runs:
  - `cargo fmt --all -- --check`
  - `cargo clippy --workspace -- -D warnings`
  - `cargo test --workspace`

This is strong local hygiene. It means the project already values quality gates before merge.

### Rust code is disciplined

From the inspected core files:

- `crates/pcfm-core/src/rng.rs` uses deterministic naming and BTreeMap-based isolation.
- `crates/pcfm-core/src/event_bus.rs` is explicit about ordering and limitations.
- `Cargo.toml` sets strict workspace lints and denies unsafe code.

This indicates a project that is consciously trying to make the Rust surface auditable and hard to misuse.

## The real gap

The project’s issue is not that the Rust code is deeply broken. The issue is that the repo does not enforce the same standards on GitHub itself.

The local hook solves only one layer:
- it protects the developer machine
- it is optional
- it is easy to bypass
- it does not create a repo-wide rule visible to contributors or maintainers

The missing layer is GitHub Actions CI combined with branch protection.

## Quick wins to apply immediately

### 1) Add GitHub Actions CI

Create `.github/workflows/ci.yml`:

```yaml
name: ci

on:
  push:
    branches: [main]
  pull_request:

jobs:
  rust-checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: dtolnay/rust-toolchain@stable
        with:
          toolchain: 1.85.0
          components: rustfmt, clippy

      - uses: Swatinem/rust-cache@v2

      - name: Check formatting
        run: cargo fmt --all -- --check

      - name: Run clippy
        run: cargo clippy --workspace -- -D warnings

      - name: Run tests
        run: cargo test --workspace
```

Why this is the highest priority:
- it closes the enforcement gap
- it protects PRs and forks
- it makes quality requirements visible and mandatory
- it matches the repo's current local standards

### 2) Document the hook installation in contributor docs

Add to `CONTRIBUTING.md` or `README.md`:

```bash
git config core.hooksPath .githooks
```

Why:
- the hook already exists, but without install instructions it is easy to miss
- it reduces variance between developers
- it turns a local rule into a repeatable repo practice

### 3) Keep the local hook, but do not rely on it alone

The current `.githooks/pre-commit` is already good. It should remain in place, but it should be treated as a local convenience layer, not the repository's only barrier.

### 4) Clean up `docs/context/analysis`

The repository should keep audit notes, but they need a retention rule. Stale analysis files should be archived or removed after being incorporated into the real repo state.

Why:
- it prevents confusion between operational notes and canonical documentation
- it keeps future AI agents from treating historical analysis as product truth

### 5) Add branch protection on `main`

Require the CI job to pass before merge.

Why:
- this converts the workflow into a repository-hard rule
- otherwise the CI remains a suggestion, not an enforcement mechanism

### 6) Add a CI badge to the README

Example:

```md
[![CI](https://github.com/liraan/pcfootballmanager/actions/workflows/ci.yml/badge.svg)](https://github.com/liraan/pcfootballmanager/actions/workflows/ci.yml)
```

Why:
- clearer project health signal
- better contributor trust
- visible evidence that the repo is actively checked

## Rust-specific observations

### Strong points

- `crates/pcfm-core/src/rng.rs` is good for a deterministic engine.
- `event_bus.rs` is explicit about dispatch semantics and known constraints.
- The workspace lints are stronger than the average Rust project.

### Real issue to track

`crates/pcfm-core/src/event_bus.rs` explicitly states that a panicking handler can propagate and lose queued events.

This is not a code smell in the usual sense, but it is a genuine design limitation and should be treated as a backlog item.

Recommended follow-up:
- add failure-path tests
- consider a `catch_unwind` boundary at the handler level
- clarify the public contract in a future ADR or code comment

## Deeper tests worth adding

### 1) Golden determinism tests

Goal: same seed + same scenario => same output hash/state.

### 2) Property-based RNG tests

Goal: validate invariants over many generated inputs.

### 3) Event-bus failure-mode tests

Goal: document behavior when a handler panics.

### 4) CLI smoke tests

Goal: protect `pcfm-demo` and test-runner behavior.

## Recommended order of action

1. Add `.github/workflows/ci.yml`
2. Require the CI check on `main`
3. Document `.githooks` installation in contributor docs
4. Archive stale analysis artifacts
5. Add a README CI badge
6. Expand the Rust test coverage with deterministic + property-based tests

## Final verdict

The repository is structurally disciplined, the Rust core is reasonably healthy, and the project already has a good local quality gate. The major gap is not code quality but repository-level enforcement. Adding GitHub Actions CI and required checks would immediately improve the project’s hygiene and make the existing standards real instead of optional.

This is the right fix because it addresses the actual weakness without destabilizing the codebase.
